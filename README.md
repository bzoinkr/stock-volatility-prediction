# Stock Volatility Prediction

This project focuses on predicting stock market volatility using data-driven and machine learning approaches. By
leveraging historical price data, statistical indicators, and advanced modeling techniques, the goal is to build a
system that can anticipate periods of high and low market fluctuation. Accurate volatility prediction is crucial for
risk management, portfolio optimization, and informed trading decisions, making this project both practically valuable
and technically challenging.

The system operates through two independent sentiment pipelines — one built on Reddit social data, one on financial
news — which run in parallel and are combined at the end into a single blended volatility prediction.

## Where Results Land

**`artifacts/`** is where all final outputs are written:

- `artifacts/predictions/` — the final prediction outputs from the social pipeline, news pipeline, and the combined blended result. This is where you look after a successful run.
- `artifacts/models/` — the trained model files. A pre-trained social model is already stored here (see note in the Running section).
- `artifacts/evaluations/` — evaluation metrics generated by the evaluation scripts (`41_evaluate_social.py`, `43_evaluate_news.py`).

**`data/`** holds the data collected and processed throughout execution. It does not contain final predictions but is essential for the pipeline to function. Raw fetched data lands in `data/raw/`, gets cleaned into `data/processed/`, and intermediate pipeline outputs (keywords, names, etc.) go into `data/interim/`.

## Getting Started

### System Requirements

No specific operating system is required — the project runs on Windows, macOS, and Linux. However, since the pipeline 
runs **Phi-4 locally via Ollama**, your machine needs enough RAM and compute to handle a mid-size LLM. Phi-4 requires at 
least **8–16 GB of RAM** and will run significantly faster with a dedicated GPU. Running it on CPU alone is possible but 
slow.

Beyond that, standard Python 3.9+ is all you need.

---

### Prerequisites

Install the required Python dependencies:

```bash
pip install -r requirements.txt
```

---

### Setting Up Ollama (Required)

This project uses **Phi-4** via [Ollama](https://ollama.com) for LLM-based keyword and peer ticker generation. Ollama
runs the model locally — no API key needed, but you do need it installed and the model pulled before running the
pipeline.

**1. Install Ollama**

Head to [https://ollama.com/download](https://ollama.com/download) and download the installer for your OS.

**2. Pull the Phi-4 model**

Once Ollama is installed, open a terminal and run:

```bash
ollama pull phi4
```

This will download the Phi-4 model weights locally. The download is a few GBs so give it a minute depending on your
connection.

**3. Make sure Ollama is running**

Ollama needs to be running in the background whenever you execute the pipeline. It usually starts automatically after
installation, but you can confirm or start it manually with:

```bash
ollama serve
```

You can verify Phi-4 is available by running:

```bash
ollama list
```

`phi4` should appear in the output.

### Configuring `configs/run.yaml`

Before running anything — regardless of which execution option you choose — configure `configs/run.yaml` to match your
intended tickers, date range, and parameters. Every script across all three options reads from this file.

**`universe`** — defines which stocks to operate on and over what time window:
```yaml
universe:
  tickers: ["Apple", "Amazon"]       # Company names (used for keyword and news search)
  ticker_symbols: ["NVDA"]           # Ticker symbols (used for fetching market data)
  start_date_news: "2025-03-18"      # Start of the news fetch window (exclusive)
  start_date: "2026-04-10"           # Start of the social data window
  end_date: "2026-04-21"             # End of the data window
  target_date: "2026-04-21"          # The specific date you want predictions generated for
```

Here is what each date field means and how to set it:

- **`target_date`** — the date you want a volatility prediction for. Everything else in the pipeline is oriented around this date.

- **`end_date`** — the last date from which data is collected. This should almost always be set to one day before `target_date`, and ideally one to two days before today for the social pipeline to ensure fresh data is available.

- **`start_date`** — the earliest date from which social (Reddit) data is collected. For predictions, set this to roughly one to two weeks before today. Going much further back is not useful since Reddit data beyond a week is increasingly unavailable (see the note below).

- **`start_date_news`** — the earliest date from which news articles are collected. Since news archives are much more accessible than Reddit history, you can and should set this further back — ideally one to two years before `target_date` — to give the news pipeline a richer training signal.

> 📅 **Note on `target_date` for social predictions:** If you are running the social pipeline, set `target_date` to
> today or tomorrow (if today is nearly over). The social pipeline relies on fetching the latest Reddit posts, and
> Reddit's search does not allow reliably retrieving posts from more than roughly a week in the past — meaning
> predictions for dates further back become increasingly impossible to generate. If the pipeline cannot find sufficient
> data for the target date, the prediction for that ticker will simply be skipped rather than producing a bad result.

**`ticker_symbols`** — this is the most important field in `universe`. It defines the exact list of stocks the pipeline will predict for. You can pass as many tickers as you want:
```yaml
ticker_symbols: ["AAPL", "MSFT", "NVDA", "TSLA"]
```

Ticker symbols must follow the **yfinance / Yahoo Finance format**, which works as follows:

- US stocks use their standard exchange symbol with no suffix — `AAPL`, `MSFT`, `GOOGL`, `AMZN`, `TSLA`, `NVDA`, etc.
- International stocks append a suffix for their exchange — for example `.TO` for the Toronto Stock Exchange (`RY.TO`), `.L` for the London Stock Exchange (`HSBA.L`), or `.DE` for the German Xetra exchange (`SAP.DE`).
- No special characters, spaces, or punctuation should appear in the symbol itself. Suffixes use a dot separator as shown above, but that is the only exception.

If you are unsure of the correct symbol for a company, look it up directly on [Yahoo Finance](https://finance.yahoo.com) — whatever appears in the URL or search result for that company is what you should use here. The `tickers` field (natural language names) is supplementary and does not drive the core predictions, so focus on getting `ticker_symbols` right.

**`prediction_ratio`** — controls the blend between social and news predictions in the final combined output. A value
of `0.0` means the final prediction is driven entirely by the social pipeline; `1.0` means it is driven entirely by
the news pipeline. The default of `0.1` gives the social pipeline slightly more influence:
```yaml
prediction_ratio: 0.1
```

**`keyword_count` / `llm_run_count`** — controls how many search keywords Phi-4 generates per ticker during the
keyword building stage, and how many independent LLM passes to run. More passes improve keyword quality at the cost
of time:
```yaml
keyword_count: 5
llm_run_count: 1
```

**`peer_count` / `news_limit_per_ticker`** — controls how many peer companies are identified per ticker for extended
data collection, and caps the maximum number of news articles fetched per ticker to keep data volumes manageable:
```yaml
peer_count: 6
news_limit_per_ticker: 10000
```

**`day_weights`** — a 5-element list representing the importance of each day in the lookback window, ordered from most
recent to oldest. The defaults apply a steep decay so that yesterday's data has significantly more influence than data
from five days ago:
```yaml
day_weights: [1, 0.5, 0.33, 0.2, 0.1]
```

**`feature_weights` / `feature_weights_news`** — per-feature importance multipliers for the social and news pipelines
respectively. Each index corresponds to a named feature, with the mapping documented inline via comments directly in
`run.yaml`. The defaults are tuned values and should only be adjusted if you have a specific reason to reweight
individual features:
```yaml
feature_weights: [1, 1, 0.1, 0.1, ...]      # social pipeline features
feature_weights_news: [1, 0.1, 0.1, ...]     # news pipeline features
```

**`output.overwrite`** — if set to `true`, existing processed data and artifacts will be overwritten on the next run.
Leave this as `false` unless you intend to regenerate outputs from scratch:
```yaml
output:
  overwrite: false
```

### Running the Pipeline

#### Option 1 — CLI Scripts (Recommended)

The `cli/` folder contains high-level scripts that handle full end-to-end workflows. These are the recommended entry
points for most users. Run all commands from the project root.

> ⚠️ **Caution:** `cli/socialTrain.py` is included for completeness but is **strongly not recommended to run**. It
> retrains the social model from scratch, which is an extremely long-running operation. More importantly, any newly
> trained model would only have seen the small amount of data you just gathered locally, whereas the pre-trained model
> bundled in `artifacts/models/` was trained on data collected over multiple days across a broad set of tickers.
> Because the full training dataset cannot be redistributed here, **the pre-trained model will almost always
> outperform a freshly retrained one** unless you have been accumulating local data over an extended period.
> There is no need to run this script under normal circumstances.

| Script | Description |
|---|---|
| `socialPrediction.py` | Runs volatility predictions using the social pipeline |
| `newsPrediction.py` | Runs volatility predictions using the news pipeline |
| `combinePrediction.py` | Blends social and news predictions into a final output |
| `socialTrain.py` | ⚠️ Retrains the social model — avoid unless necessary |

```bash
python cli/socialPrediction.py
python cli/newsPrediction.py
python cli/combinePrediction.py
```

#### Option 3 — Retraining the Social Model (High Caution)

The `scripts/train_social/` folder contains heavier variants of certain pipeline steps intended for retraining the
social model on new data. These scripts are designed to be run **in place of** their `scripts/` counterparts for the
affected stages — not in addition to them:

| Replace | With |
|---|---|
| `scripts/03_fetch_market_volatility_target.py` | `scripts/train_social/032_fetch_market_volatility_compound.py` |
| `scripts/04_fetch_social_target.py` | `scripts/train_social/042_fetch_social_train.py` |
| `scripts/11_execute_vader.py` | `scripts/train_social/112_execute_vader_train.py` |
| `scripts/21_clean_social_data.py` | `scripts/train_social/212_clean_social_data_train.py` |

```bash
python scripts/train_social/042_fetch_social_train.py
# etc.
```

> 🔴 **High Caution:** These scripts overwrite training artifacts and are destructive by design. Only run them if you
> explicitly intend to retrain the model. The codebase is built to support incremental data accumulation — you can
> keep running these scripts over time to grow your local training dataset before triggering a retrain, which will
> improve model quality compared to training on a single day's data.
